# PWA service worker: hand-rolled runtime-caching, no precache

> Make the player installable with a ~40-line hand-rolled runtime-caching service worker (no Workbox,
> no precache manifest), keeping the project's zero-dependency ethos while staying un-brickable.

**Date:** 2026-07-31  **Status:** accepted

## Context

Making the app installable (standalone launch, app icon, offline shell) requires a service worker:
Chrome/Android only grant a true install (WebAPK, not a shortcut) when a SW with a fetch handler is
registered. The hazard is that a SW lives on the client and **can't be edge-purged** — a SW that
caches HTML/JS wrong can permanently white-screen returning users. This is the [[deploy-cloudflare]]
cache-poisoning incident, but unrecoverable-by-purge.

## Options considered

- **A — `vite-plugin-pwa` / Workbox (generateSW or injectManifest).** Battle-tested precache-manifest
  revisioning. But its whole value proposition is *precache correctness*, and it adds a build
  dependency to a project whose ethos is only `react`/`react-dom` + hand-rolled `scripts/*.ts`.
- **B — hand-rolled runtime-caching SW, no precache.** Network-first navigations + cache-first for
  immutable hashed `/assets/*` + network-first (cache-fallback) for other same-origin assets, nothing
  precached. The scout (`architect`) recommended A; we override to B.
- **C — hand-rolled SW *with* a precache list derived from `dist/`.** Re-derives the exact
  atomic-activation/revisioning that bricks precache SWs, by hand, untested. Rejected.

## Decision

**B.** The architect's case for buying Workbox rests entirely on precache-manifest revisioning being
the brick-prone part. We avoid precache altogether, which collapses that justification: our JS/CSS
are content-hashed + `immutable`, and the app is a single-screen SPA that fetches its whole shell on
first paint — so cache-first-on-`/assets` (immutable) + network-first for the rest + network-first
navigation captures the full shell as it's fetched (from the reload after the first visit, since the
default lifecycle only controls the next navigation) with **nothing to revision across deploys**.
`public/sw.js` is ~60 lines we own.

Brick-avoidance rests on framework-independent invariants:
1. `sw.js` served `Cache-Control: max-age=0, must-revalidate` (`public/_headers`) → a fix propagates
   on the browser's revalidation; never `immutable`.
2. Navigations are network-first → a bad deploy's HTML always comes from the network while online.
3. Default lifecycle (no `skipWaiting`) → no mid-session chunk swap.
4. A documented self-destruct recovery SW ([[pwa-recovery]]) — the client-side "purge everything".

Sub-decisions: **offline audio is out of scope** (63 MB is quota-fragile, low v1 value — Media
Session already gives OS integration); **icons reuse `scripts/extract-art.ts`** (no new pipeline);
**update strategy is the default lifecycle** (immutable assets ⇒ no staleness ⇒ no update prompt).

## Consequences

- No new runtime/build dependency; the SW is auditable in one short file.
- Offline works for the shell only, and only after a first visit — acceptable, documented.
- We now own SW correctness. The `no-cache` header on `sw.js` is load-bearing and must survive any
  future `_headers` edit — it's the only thing making a bad SW recoverable.
- Offline audio, an in-app install button, and an update toast are parked in `backlog.md`.
